# Архитектура scanner_v2

Следующий рабочий срез универсальной инвентаризации, запуск, ограничения и
матрица поддержки описаны в `docs/scanner_v2_inventory.md`.

## Что изменено

Рефакторинг сохраняет существующий сканер камер как совместимый профиль.
Перечисленные будущие протоколы **не объявлены реализованными**: подготовлен
общий контракт для их подключения без зависимости от `CameraResult`.

```text
web/routers/scanner_v2.py       прежний HTTP API
            |
cameras/scanner_v2/engine.py   жизненный цикл задания, sweep/capture/геолокация
            |
       stage2_proto.py        совместимый фасад probe_host_v2()
            |
       profile.py            состав проб, фильтры, кандидаты портов
            |
ip2domain/scanning/           независимое ядро
    models.py                endpoint → service → device classification
    registry.py              явный упорядоченный реестр ProbeSpec
    runner.py                лимиты, таймауты, ошибки, отмена
            |
cameras/scanner_v2/protocols/ существующие сетевые реализации
            |
       aggregation.py        чистая проекция результатов в CameraResult
            |
core/storage/scanner_v2.py    прежние таблицы и JSON
```

Ядро не импортирует камеры, HTTP API, SQLite, ffmpeg или геобазу.
Импорт модели камеры больше не загружает весь pipeline. Публичные импорты
`run_v2_scan_pipeline` и функций из `protocols` остаются доступными лениво.

## Почему не дерево «один IP = один тип устройства»

Один IP может одновременно предоставлять веб-интерфейс, видео, телефонию
и управление. Один RTP-сервис может относиться к `video` и `voice`.
Открытый порт сам по себе не доказывает ни протокол, ни тип оборудования.

Поэтому разделены:

* `Endpoint(port, transport)` — сетевой адрес сервиса внутри хоста; TCP и UDP
  на одинаковом номере порта различаются.
* `ServiceObservation(protocol, endpoint, categories, attributes)` —
  обнаруженный сервис, с несколькими категориями при необходимости.
* `DeviceClassification(kind, evidence, confidence)` — отдельная гипотеза
  о типе устройства с основаниями, а не вывод из одного номера порта.
* `ProbeData` — нормализованный результат пробы.
* `ProbeOutcome` — идентификатор пробы, результат либо ошибка/таймаут.
* `HostObservation` — результаты хоста, не требующие видеопотока.

Категории — расширяемые строковые идентификаторы: `web`, `video`, `voice`,
`management`, `industrial`, `iot`, `storage`. Типы устройств и протоколы
также не ограничены перечислением в ядре. Наличие имени категории ничего
не включает автоматически и не добавляет новые порты к текущему sweep.

## Подключение нового протокола

1. Реализовать асинхронную функцию `ProbeContext -> ProbeData` в адаптере
   соответствующего домена. Она не должна обращаться к роутеру или БД.
2. Вернуть подтверждённые сервисы и, при наличии оснований, классификации.
3. Добавить `ProbeSpec` в явно собранный реестр профиля: идентификатор,
   функцию, предикат применимости, таймаут и категории.
4. Запускать `ProbeRunner.probe(context)`; новый runner не требует ни
   `CameraResult`, ни захвата кадров, ни изменений в legacy-агрегаторе.
5. Добавить тесты на ответы протокола, отрицательный результат, таймаут
   и отмену. Интеграционные проверки проводить на разрешённом стенде.

Пример композиции с **уже реализованной разработчиком** функцией `probe_mqtt`
(сама MQTT-проба в этот рефакторинг не входит):

```python
from ip2domain.scanning import Endpoint, ProbeContext, ProbeRegistry, ProbeRunner, ProbeSpec

registry = ProbeRegistry([
    ProbeSpec(
        probe_id="mqtt",
        run=probe_mqtt,
        applies=lambda ctx: 1883 in ctx.ports("tcp"),
        timeout=3.0,
        categories=("iot",),
    ),
])
runner = ProbeRunner(registry, concurrency=8)
context = ProbeContext("192.0.2.10", (Endpoint(1883),))
observation = await runner.probe(context)
document = observation.to_dict()
```

Реестр неизменяем: `extend()` возвращает новый экземпляр, дубликаты
идентификаторов запрещены. Нет глобального автопоиска и запуска плагинов
при импорте. Предикат `applies` определяет политику выбора; ядро не трактует
поля категорий как автоматический фильтр.

## Совместимость камер

`probe_host_v2(ip, open_ports, credentials, protocols)` по-прежнему возвращает
`CameraResult | None`, а сериализация, роуты и существующая БД не меняются.
В `aggregation.py` перенесены прежние правила объединения **без изменения
приоритетов**: ONVIF/вендоры/VMS/SpRecord, URL, авторизация и эвристики портов.
HTTP-детектор вынесен в `protocols/generic_http.py`.

Сохранены даже особенности старого фильтра:

* `protocols=None` и `protocols=[]` означают стандартный набор;
* SpRecord, Ingram и generic HTTP запускаются независимо от фильтра;
* Sofia и DHIP дополнительно активируются портами/алиасами;
* RTSP и RTMP запускаются только при наличии соответствующих портов;
* порядок пользовательских портов в HTTP-fallback сохранён.

В нейтральном контексте `None` и пустой набор различимы; конкретный профиль
решает, какие пробы являются обязательными.

`probe_host_observation_v2()` даёт доступ к диагностике каждой пробы до
проекции. Legacy payload хранится в `ProbeData.attributes` для адаптера,
но не включается в `HostObservation.to_dict()` или `repr`: там могут быть
учётные данные. Это **не универсальная очистка произвольных данных**:
новые адаптеры обязаны не помещать секреты в публичные атрибуты сервисов.
Старый `CameraResult.to_dict()` намеренно сохраняет прежний контракт
с credentials; его политика доступа не изменена.

## Выполнение и ресурсы

* Этапы 2 и 3 используют `run_bounded`: число задач пропорционально лимиту
  рабочих задач, а не числу обнаруженных хостов.
* Ошибка отдельной пробы не уничтожает результаты остальных.
* Результаты проб возвращаются в порядке реестра независимо от порядка
  завершения. Это сохраняет детерминированность legacy-проекции.
* Внешняя отмена пробрасывается; дочерние задачи отменяются и дожидаются
  завершения. Кооперативная отмена прекращает выдачу новых хостов.
* Один `ProbeRunner` можно переиспользовать в пределах одного event loop:
  его лимит будет общим для всех вызовов.
* Камерный фасад сохраняет прежнюю параллельность внутри хоста: свой runner
  на вызов, 14 зарегистрированных проб и лимит 16. Внешний лимит хостов
  остаётся `stage2_concurrency`, общий таймаут хоста — 35 секунд.
* У legacy-проб не введён новый сокращающий таймаут: их собственные
  таймауты и внешний бюджет сохранены. Новые профили задают `ProbeSpec.timeout`.

## Что остаётся следующим этапом

Это не полная миграция приложения на универсальный инвентаризатор.
Перед включением новых доменов в пользовательский интерфейс нужно:

1. Добавить нейтральное хранилище хостов/сервисов/наблюдений и API поверх
   версионированного `HostObservation`, не перегружая таблицу камер.
2. Определить профили sweep, включая отдельную стратегию UDP. Наличие
   `Endpoint(..., "udp")` не означает, что старый TCP sweep сканирует UDP.
3. Разделить post-processing по возможностям: кадры только для видео,
   аудио — отдельно, инвентаризация — без требования медиапотока.
   Старый камерный stage 3 пока сохраняет прежнюю фильтрацию.
4. Выделить репозиторий заданий и пересмотреть checkpoint/resume.
   Текущий индекс sweep не является полным checkpoint всего pipeline.
5. Отдельно вынести конфигурацию, transport clients и политику credentials
   из существующих сетевых реализаций. Новое ядро не добавляет перебор
   паролей и не меняет существующий модуль авторизации.
6. Перевести целевые адреса и результаты sweep на потоковую обработку:
   `run_bounded` устраняет миллионы asyncio-задач, но текущие списки целей
   и responsive_hosts по-прежнему материализуются.

Изменения транспорта, эвристик идентификации и схемы БД следует проводить
отдельно от структурного рефакторинга, с миграциями и контрактными тестами.

## Проверка

Новые тесты:

* `tests/test_scanning_core.py`: расширение реестра, TCP/UDP,
  несколько категорий, результаты без видео, исключения, таймауты,
  общий лимит, ленивые рабочие задачи, отмена и очистка задач.
* `tests/test_scanner_v2_architecture.py`: legacy-фильтры и порты,
  приоритеты объединения, SpRecord, fallback, независимость импортов,
  pipeline с подменёнными сетевыми операциями и временной SQLite.

Пример запуска из корня проекта (БД обязательно временная):

```bash
IP2DOMAIN_DB_PATH=/tmp/ip2domain-scanner-tests.db .venv/bin/python -m pytest \
  tests/test_scanning_core.py tests/test_scanner_v2_architecture.py \
  tests/test_scanner_v2.py tests/test_scanner_v2_bruter.py \
  tests/test_scanner_v2_coverage.py tests/test_v2_protocols.py -q
```
