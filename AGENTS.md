# Инструкции для работы с ip2domain

## Рабочий подход

- Доводи запрос до готового, проверенного результата. Рутинные решения принимай самостоятельно; уточняй только существенные неизвестные, от которых зависит результат.
- Выполняй уже разрешённую работу до запроса дополнительного согласования. Учитывай ранее полученные разрешения, не запрашивай их повторно.
- Сохраняй цель задачи при уточнениях и побочных вопросах пользователя. После ответа продолжай незавершённую работу.
- Инструкции пользователя имеют приоритет над рекомендациями навыков и этого файла в пределах системных ограничений. Если навык блокирует работу, укажи конкретный SKILL.md и правило.
- Отвечай по-русски, кратко и предметно: результат, существенные изменения, проверки и оставшиеся ограничения. При длительной работе сообщай о прогрессе.
- Независимые чтения и проверки можно выполнять параллельно. Субагентов запускай только по явному запросу пользователя; задавай им ограниченные независимые задачи.

## Контекст проекта

- Python-пакет и CLI: `ip2domain/cli.py`; зависимости и entry point — `setup.py`, дополнительные зависимости — `requirements.txt`.
- Веб-приложение FastAPI: `ip2domain/web/app.py`, маршруты — `ip2domain/web/routers/`, интерфейс — `templates/` и `static/` внутри `ip2domain/web/`.
- Основная логика и SQLite: `ip2domain/core/`, хранилище — `ip2domain/core/storage/`; провайдеры — `ip2domain/providers/`.
- Сканеры камер — `ip2domain/cameras/`, общие компоненты сканирования — `ip2domain/scanning/`; проверки — `tests/`.
- Перед изменением подсистемы прочитай соответствующий код, тесты и относящиеся к задаче разделы `README.md`, `TZ.md` и `docs/`. Документация описывает проект, но не расширяет текущий запрос автоматически.

## Изменения и проверки

- Сначала проверь `git status --short`. Сохраняй существующие изменения пользователя; ограничивай diff текущей задачей.
- Используй `rg` для поиска и существующее окружение `.venv`. Не редактируй копии исходников в `build/` и `dist/`.
- Для тестов задавай `IP2DOMAIN_DB_PATH` до импорта приложения и используй отдельную временную БД. Рабочие БД, WAL/SHM, `.env`, логи и файлы захватов не должны становиться тестовыми данными или попадать в коммит.
- Пример запуска целевых тестов из корня репозитория:

  ```bash
  test_dir=$(mktemp -d /tmp/ip2domain-tests.XXXXXX)
  IP2DOMAIN_DB_PATH="$test_dir/test.db" .venv/bin/python -m pytest tests/test_ip_parser.py -q
  ```

- Выбирай тесты изменённой подсистемы и необходимые проверки смежных контрактов. Расширяй набор при изменениях общего хранилища, API, авторизации или при обнаруженных регрессиях.
- Для исправления поведения добавляй проверку наблюдаемого результата. Для небольших правок документации и настроек достаточно проверки содержимого, синтаксиса и diff.
- Не повторяй успешно завершённые проверки без новых изменений или конкретной причины. Честно указывай, что запускалось и что осталось непроверенным.
- Сетевые взаимодействия в тестах изолируй моками или локальными фикстурами. Перезапуск сервиса и реальные сканирования выполняй только в рамках соответствующей задачи и согласованного охвата.
- Не ослабляй авторизацию, ограничения целей и таймауты ради прохождения тестов.

## Настройка Codex

Проектная модель задана в `.codex/config.toml`: `gpt-6-astra`. Уровень reasoning наследуется из настроек пользователя или значения модели по умолчанию. Этот файл задаёт поведение агента, но не переключает модель уже запущенной сессии и не включает API-функции оркестрации.

Основа поведенческих правил — [OpenAI Docs: GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra), проверено 2026-09-07. Настройки проекта описаны в [Codex Config basics](https://learn.chatgpt.com/docs/config-file/config-basic); проектный config загружается для доверенного проекта, а явные параметры запуска имеют приоритет.
